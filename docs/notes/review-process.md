# Expert review panel (UX / UI / answer / dataviz / personas)

Use when the owner asks for expert review of a flow or page, or before a design round. He wants the experts (subagents), not himself, to review.

1. Screenshots of every state at 390 px @2x (empty, typeahead, mid-flow, answer, DE, desktop 1280) with Playwright and `--font-render-hinting=none`, one folder, files named by state.
2. ONE brief file: product rules, the page flow, the definition of every number, which files may be read (read-only), output schema `{verdict, findings[{id,severity,problem,evidence,change,why,effort}], keep, top5, extra}`. Put only a pointer to it in each child's context: a literal placeholder like `@@SHARED@@` is not expanded; if it slips through, steer each child to the file.
3. Five lenses in parallel (they finish in 4-12 min): UX flow, answer presentation / risk communication, UI visual, dataviz (what the shipped data supports; what extra data would unlock, with file size), first-time personas (commuter with the app open, anxious infrequent rider, rider in a hurry on the platform, fixed-ticket rider, reader of the German page who does not speak German). Each child writes its JSON to a file; completion text can be truncated or late.
4. Before reporting, check any claim that sounds like a data bug against the raw data. One reviewer noticed rows in non-clock order; the root cause was timetable variants in the data job, so the data was fixed before the UI.
5. Consolidate into a PLAN.md: what all lenses agree on (build), what is editorial judgement (verdict words, advice: leave out until the owner decides), what is bigger (extra data, later). Report in plain language with one decision; build on the branch, run every suite, send new German strings to the German reviewer, give the preview URL, publish only on his yes (unless he has said to push once the reviewers are happy: then a clean final round is the go, see docs/RULES.md).

## Whole-site mobile critique + design mocks
Use when he says the phone UI is bad overall (not one flow) and asks for a reviewer plus HTML mocks on a contact sheet.
1. Work in `a local design folder (not in the repo)` (not scratch, which other sessions wipe): `shots/`, `scripts/`, `BRIEF.md`.
2. One Playwright script captures every page type of the LIVE site at 390x844 @2x, `isMobile`, `--font-render-hinting=none`, after `document.fonts.ready`: `<page>.png` (first viewport) and `<page>-full.png` (full page, clip height capped ~5200 px so huge pages stay light), plus search focus/typing states. Page set: home, home-de, one route (hamburg-hbf-berlin-hbf), one train (ice-1541), change, ranking, network, routes, compensation, recap. One browser, fresh context per page, closed in `finally`. Run with the repo Node from docs/RULES.md's PATH line (the system node is too old for Playwright).
3. Dump `main.innerText` of route/train/ranking/change to text files: mocks must use real copy and numbers, not invented ones.
4. BRIEF.md: his complaint, the locked rules (direction B tokens, one number per view, DB 6-min beside 15-min, four tabs and no More, search lands on destination, deadpan), screenshot paths with a note to crop tall full pages via the vision region parameter, read-only source paths, no-browser rule, and an output schema with `per_page` proposed phone layouts and `patterns` (naming the app that does each). One reviewer child gets only a pointer to the brief and writes `critique.json`.
5. While it runs, gather inputs that don't depend on it (tokens from `app/globals.css`, local Archivo woff2 in `a local design folder (not in the repo)`, the text dumps), then end the turn. Build the mocks from the critique's per_page layouts (phone-frame board per product-ui-refinement `references/mobile-screen-prototypes.md`, current vs proposed side by side, DECIDE tags on real product choices), render one Chromium at a time, vision-check, deliver contact-sheet images.
8. He approved the mocks with "build this, verify, and push": that one message is the publish go. Build on a branch, send new German strings to the reviewer in parallel with the build, run suites + full-site crawl, push, poll a marker only the new build has, rerun the suite with `BASE=` prod.

## Review rounds for rights/legal page copy
One pass is not enough. Round 1 finds framing and overstated sentences; applying its fixes can introduce or leave gaps that only a fresh reader with the primary text catches (clock start of a time limit, through-ticket rules, which condition a cap hangs on). Loop: full-copy review by independent readers (EN rights and DE in parallel) -> apply -> fresh readers on the rewritten full copy -> apply -> a narrow check of only the changed strings. Give every round the same brief file plus a copy file of key / EN / DE, the primary-source text and the verified rules JSON; require `ok_to_publish` and a must_fix list limited to real accuracy or misleading issues. Reviewers' optional polish notes are cheap to apply from their exact wording before pushing.
